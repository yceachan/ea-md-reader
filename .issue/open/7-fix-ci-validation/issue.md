# CI 验证组织改进草案

CI 应执行所有具备运行条件的检查，集中报告发现的失败和未执行项。一次运行不能证明不存在偶发故障；平台限制、前置条件和测试场景决定实际验证范围。本条目仅记录待确认的需求与路线，尚未实施测试拆分或 workflow 修改。

## 原始需求

> 可以让 CI 尽量执行完所有可运行的测试，集中报告失败和未执行项。
> 第一阶段先拆分当前编辑器与 Reader 的两个长测试，再调整步骤依赖、完善汇总，最后补齐竞态和被跳过场景。
> 自动重试通过不能当作问题解决，应保留首次失败信息。

保留矩阵 `fail-fast: false`，各失败步骤保持失败状态，整体 CI 仍告红。用户取消运行时停止继续启动测试，报告收集已有结果。

## 当前问题

- `tests/editors.spec.cjs` 的“文件树中键与非活动标签菜单编辑正确目标，同路径标签自动更新而标签中键只关闭”串联外部编辑、标签更新、滚动进度、标签关闭、编辑器选择与持久化；前段断言失败会遮挡后段行为。
- `tests/reader.spec.cjs` 的“工作区切换、右键菜单、面板拖拽与容器自适应”串联文件操作和多种布局，缺少行为间的环境隔离。
- `.github/workflows/ci.yml` 将类型检查、构建、打包、Node 测试和源码 UI 按默认成功条件串联。Linux sandbox 准备同时引用开发版和打包版路径，使源码 UI 额外依赖打包结果。
- DevTools 生命周期用例在 `tests/commands.spec.cjs` 中无条件跳过。Windows Shell 只允许在专用 Windows 11 桌面执行，不能借普通矩阵的通过状态推断其已验证。
- 当前上传 HTML 报告及运行产物，没有集中区分平台不适用、主动跳过、前置条件阻塞和取消。

## 目标与范围

将长测试拆为独立场景，每项独立建立临时文件、用户配置和 Electron 会话，只共享必要的环境准备与清理辅助函数。保持现有平台保护和测试桌面隔离，不增加测试并发，不通过忽略失败或提高重试次数制造绿色结果。

编辑器测试拆为外部编辑与同路径标签刷新、滚动与进度保持、标签关闭、编辑器选择与持久化。Reader 测试拆为工作区操作、面板拖拽、窄屏覆盖层、宽屏排版。

文件打开、标签切换和正文渲染属于前置条件，仍使用普通断言。同一已就绪布局内独立的宽度、留白和按钮位置可使用 `expect.soft`；一个检查失败时，其他独立检查继续采集。

## 拟定执行依赖

| 检查或操作 | 必要前置条件 |
| --- | --- |
| 类型检查、纯 Node 测试 | Node 与 npm 依赖安装成功 |
| 平台工具相关 Node 测试 | npm 依赖及该组所需系统工具准备成功 |
| 构建 | npm 依赖及构建工具准备成功 |
| 源码 UI | 构建成功，源码 Electron 运行环境就绪 |
| 打包 | 构建成功 |
| 打包应用测试 | 打包成功，打包 Electron 运行环境就绪 |
| DevTools 独立测试 | 构建成功，对应平台的隔离桌面就绪 |
| Windows Shell | 专用 Windows 11 CI 桌面、Explorer 与构建就绪 |
| 汇总与上传 | 始终尝试收集已有结果 |

源码和打包应用的 Linux sandbox 准备分别执行，互不增加产物依赖。为依赖步骤设置稳定 ID，测试条件使用 `!cancelled()` 与必要前置步骤的 `outcome`，不依赖所有之前步骤都成功。不为测试使用 `continue-on-error`，报告与上传可使用 `always()`。[GitHub 条件表达式](https://docs.github.com/zh/actions/reference/workflows-and-actions/expressions)

## 汇总契约

按平台、架构和测试组列出：通过、失败、跳过、前置条件阻塞、取消。跳过区分平台不适用和待启用场景，并给出原因。通过重试的用例单独标注 flaky，保留首次失败、后续尝试及日志。

步骤状态与结构化测试结果共同参与汇总。报告文件不存在时按实际前置条件标为阻塞或执行失败，不当作零失败、零跳过。未触发的独立 Shell 工作流明确标为“本轮未验证”。失败、trace、截图和进程退出信息保存在 `artifacts/`；交付正文只引用证据并写验证结论。

报告步骤本身的失败也需要可见，不能覆盖原测试失败。取消时尽力收集已经产生的结果，不保证被强制终止的 runner 能完成上传。

## 实施顺序

1. 拆分两个长测试，核对原断言均有归属，分别运行各场景。
2. 调整步骤依赖并分开准备 Linux sandbox；验证类型检查、Node、源码 UI 或打包单独失败时，其他满足条件的检查仍能运行。
3. 为 Node、源码 UI、打包应用和独立步骤产生结构化结果，生成集中摘要，验证失败与未执行原因可区分。
4. 将 DevTools 放入独立步骤与独立结果目录，启用后真实运行；保留 Windows Shell 专用桌面限制。
5. 构造渲染进行中发生用户滚动的受控场景，渲染完成后检查最终位置和进度。针对该场景有限重复，建议三次独立执行，不以测试重试替代修复。

## 验收标准

- 拆分后的行为可单独运行，前一行为失败不遮挡后一行为，原有有效断言未丢失。
- 类型检查或某组测试失败后，所有仍具备运行条件的检查继续；缺少前置条件的组不会启动，摘要说明阻塞原因。
- 源码 UI 不依赖打包成功，打包应用测试只在包及运行环境就绪后执行。
- 任一检查失败时整体 CI 保持失败；用户取消后不继续启动测试。
- 摘要覆盖失败、跳过、阻塞、取消与 flaky；未生成测试结果的组不被视为通过。
- DevTools 和 Windows Shell 各有明确的已验证或未验证状态，保留平台与专用桌面限制。
- 滚动竞态用例控制渲染与滚动的先后关系，有界重复保留每次结果和首次失败信息。

## 待确认决定

本草案推荐先完成测试拆分、依赖和汇总，再单独恢复 DevTools 与处理滚动竞态。实现时确定结构化报告格式和汇总入口；尚未形成已采纳 ADR，也不在本轮扩展测试场景或更改 CI。
